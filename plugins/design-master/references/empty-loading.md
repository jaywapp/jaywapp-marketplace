# 빈 화면과 로딩 (빈 화면 9종, 로딩 패턴 9종)

내용이 없거나 기다려야 하는 순간의 화면이다. 이 상태를 비워 두면 화면이 고장 난 것처럼 보인다. 완성 연출은 [indicators-completion.md](indicators-completion.md), 오류 문구 형식은 [feedback.md](feedback.md).

빈 화면 공통 규칙: 이유 한 줄, 다음 행동 버튼 하나, 일러스트는 선택(작게). 오류를 사용자 탓으로 쓰지 않는다. 원인별로 문구와 행동이 다르므로 한 "빈 화면"으로 뭉치지 않는다.

## A. 빈 화면 9종

### 첫 사용 (First use)
- 무엇: 아직 데이터가 하나도 없는 처음의 화면(빈 목록, 빈 대시보드).
- 언제: 가입 직후, 첫 프로젝트 만들기 전.
- 피할 때: 빈 표를 그대로 보여 주는 것. 예시 데이터를 진짜 데이터처럼 섞는 것.
- 구현 주의: 이 화면이 무엇을 위한 곳인지 한 문장, 첫 행동 버튼 하나(`첫 항목 추가`). 샘플을 채울 때는 샘플임을 표시하고 지우기 쉽게 한다.
- 비슷한 것: 온보딩([onboarding.md](onboarding.md), 앱 전체 소개), 모두 완료(과거에 있다가 비었다).

### 검색 결과 없음 (No search results)
- 무엇: 검색어에 맞는 결과가 없는 화면.
- 언제: 검색 후 결과가 0건일 때.
- 구현 주의: 입력한 검색어를 문구에 보여 준다. 오타 확인, 더 짧은 검색어, 인기 항목이나 추천 같은 다음 길을 제시한다. 검색창은 그대로 둔다.
- 비슷한 것: 필터 결과 없음(검색어가 아니라 조건이 문제).

### 필터 결과 없음 (No filter results)
- 무엇: 적용한 필터 조합에 해당하는 항목이 없는 화면.
- 언제: 필터를 걸어 결과가 0건일 때.
- 구현 주의: 적용된 필터를 보여 주고 `필터 초기화` 버튼을 바로 둔다. 원인이 되는 필터를 하나씩 해제할 수 있게 하면 더 좋다.
- 비슷한 것: 검색 결과 없음.

### 오프라인 (Offline)
- 무엇: 네트워크가 없어 내용을 불러올 수 없는 화면.
- 언제: 연결 끊김 감지 시.
- 구현 주의: 이전에 받은 내용이 있으면 가리지 말고 보여 주고 상단에 배너로 알린다. 없을 때만 전체 빈 화면. `다시 시도` 버튼, 연결이 돌아오면 자동 재시도. 저장 대기 중인 작업이 있으면 알린다.
- 비슷한 것: 오류 화면(서버나 코드 문제).

### 권한 필요 (Permission needed)
- 무엇: 카메라, 위치, 알림 등 시스템 권한이 없어 기능을 쓸 수 없는 화면.
- 언제: 권한을 거부했거나 아직 요청하지 않은 상태에서 해당 기능에 진입했을 때.
- 구현 주의: 왜 필요한지 한 문장, `권한 허용` 버튼(시스템 요청 가능하면 요청, 이미 영구 거부면 설정 앱으로 안내). 권한 없이 쓸 수 있는 대안이 있으면 같이 보여 준다. 요청 전 사전 설명은 [onboarding.md](onboarding.md)의 권한 요청.
- 비슷한 것: 잠김(권한이 아니라 자격이나 결제 문제).

### 모두 완료 (All caught up)
- 무엇: 처리할 것이 모두 끝나 목록이 비어 있는 긍정적인 빈 상태.
- 언제: 알림을 다 읽음, 할 일을 모두 끝냄.
- 구현 주의: 짧게 칭찬하고 끝낸다. 다음에 할 만한 것을 한 가지 제안해도 된다. 과한 축하 연출은 반복 방문 시 피로하다. 완료 연출은 [indicators-completion.md](indicators-completion.md).
- 비슷한 것: 첫 사용(시작 전의 빈 상태).

### 삭제 직후 (Emptied)
- 무엇: 사용자가 마지막 항목을 지워 목록이 방금 비게 된 화면.
- 언제: 마지막 항목 삭제 직후.
- 구현 주의: 사라진 순간 갑자기 레이아웃이 바뀌지 않게 부드럽게 전환한다. 되돌리기를 [스낵바](feedback.md)로 제공하고, 빈 화면 문구는 첫 사용과 다르게 "모두 지웠어요"처럼 상황에 맞춘다.
- 비슷한 것: 첫 사용(한 번도 없었다).

### 오류 화면 (Error state)
- 무엇: 서버나 알 수 없는 문제로 내용을 보여 줄 수 없는 화면.
- 언제: 요청 실패, 예기치 않은 예외.
- 구현 주의: 무슨 일이 일어났는지 쉬운 말, 재시도 버튼, 계속 안 되면 문의 방법. 기술 메시지는 접어 두거나 복사 가능하게 둔다. 부분 실패는 화면 전체가 아닌 해당 영역만 오류로 바꾼다.
- 비슷한 것: 오프라인(사용자 쪽 연결 문제), 인라인 오류(입력 칸 하나).

### 잠김 (Locked content)
- 무엇: 로그인, 구독, 승급 같은 조건 없이는 볼 수 없는 내용을 알리는 화면.
- 언제: 유료 기능, 멤버 전용 콘텐츠, 연령 제한.
- 구현 주의: 무엇이 잠겼는지 보이고(흐린 미리보기), 풀리는 조건과 `로그인`이나 `업그레이드` 행동을 명확히. 숨기기만 하면 기능 존재를 모른다.
- 비슷한 것: 권한 필요(기기 권한).

## B. 로딩 패턴 9종

공통 기준(이 문서가 시간 기준의 유일한 출처이고 다른 문서는 여기를 가리킨다):
- 0.3초 미만: 표시하지 않는다(지연 표시로 깜빡임 방지).
- 0.3~1초: 작은 스피너.
- 1초 이상이면서 화면 구조를 아는 경우: 스켈레톤.
- 10초 이상: 진행률과 취소 방법.
- 실패했을 때의 화면도 함께 정한다.

### 스피너 (Spinner)
- 무엇: 돌아가는 원 모양의 진행 중 표시. 얼마나 걸릴지 모를 때 쓴다.
- 언제: 짧은 대기(공통 기준의 0.3~1초)나 결과 모양이 정해지지 않은 대기, 버튼이나 작은 영역 안.
- 피할 때: 전체 화면을 스피너 하나로 채우는 긴 로딩(스켈레톤), 진행률을 알 수 있는 업로드(진행 바).
- 구현 주의: 크기 16~24px(버튼 안), 32~48px(영역). 색 대비 3:1. `role="status"`와 읽히는 텍스트(`불러오는 중`). 모션이 거슬려도 회전은 허용되는 관례이지만 `prefers-reduced-motion`이면 느리게 하거나 정적 표시로 바꾼다. 0.3초 이내에 끝나면 보이지 않게 지연 표시.
- 비슷한 것: 스피너 vs 스켈레톤([confusable-pairs.md](confusable-pairs.md)).

### 스켈레톤 (Skeleton screen)
- 무엇: 실제 내용이 들어갈 자리의 윤곽을 회색 블록으로 먼저 보여 주는 로딩 화면.
- 언제: 목록, 카드, 프로필처럼 구조가 정해진 화면의 첫 로딩. 1초 넘는 대기.
- 피할 때: 구조를 알 수 없는 내용, 아주 짧은 로딩(깜빡임), 로딩 후 레이아웃이 크게 달라질 때.
- 구현 주의: 실제 콘텐츠와 같은 크기, 같은 간격으로 만든다(로딩 후 레이아웃 이동 방지). 반짝이는 효과(shimmer)는 1.5~2초 주기로 약하게, `prefers-reduced-motion`이면 정지. 보이는 블록에는 `aria-hidden`을 두고 전체 영역에 `aria-busy="true"`. 앱 첫 화면에서의 사용은 [onboarding.md](onboarding.md).
- 비슷한 것: 블러 업(이미지 하나의 점진적 표시), 스피너.

### 진행 바 (Progress bar)
- 무엇: 가로 막대가 채워지며 전체 중 어디까지 진행됐는지 보여 주는 표시.
- 언제: 진행률을 알 수 있는 업로드, 다운로드, 처리. 페이지 상단의 이동 중 표시.
- 피할 때: 끝을 알 수 없는 작업(스피너나 불확정 바), 아주 짧은 작업.
- 구현 주의: 두께 4~8px, 트랙과 채움의 대비 3:1. `role="progressbar"`, `aria-valuenow`, `aria-valuemin`, `aria-valuemax`. 퍼센트나 남은 시간을 글로도 보여 주면 좋다. 진행이 되돌아가지 않게 한다. 인디케이터 쪽 설명은 [indicators-completion.md](indicators-completion.md)에서 이 항목을 가리킨다.
- 비슷한 것: 진행 링(공간이 좁거나 원형), 스텝 인디케이터(단계 단위).

### 진행 링 (Progress ring)
- 무엇: 원형 테두리가 채워지며 진행률을 보여 주는 표시.
- 언제: 공간이 정사각형에 가까운 곳(아이콘 옆, 카드 안), 목표 달성률, 타이머.
- 피할 때: 좁고 긴 공간, 여러 개의 진행을 비교하는 화면(바가 비교하기 쉽다).
- 구현 주의: SVG `circle`의 `stroke-dasharray`로 구현. 시작 지점은 12시 방향. 중앙에 퍼센트를 글로 쓰면 읽기 쉽다. `role="progressbar"`와 값 속성. 인디케이터 쪽 이름은 원형 진행률.
- 비슷한 것: 진행 바.

### 단계 표시 (Stepper)
- 무엇: 여러 단계로 이루어진 흐름에서 현재 위치를 보여 주는 표시.
- 언제: 가입, 결제, 설정처럼 순서가 있는 여러 화면.
- 구현 주의: 본문은 [indicators-completion.md](indicators-completion.md)의 스텝 인디케이터에 있다. 로딩 맥락에서는 처리 단계를 문장으로 보여 주는 방식(`파일 확인 중 → 변환 중 → 완료`)도 쓴다.
- 비슷한 것: 스테퍼 vs 슬라이더에서의 스테퍼는 다른 요소(숫자 증감 입력).

### 블러 업 (Blur-up image)
- 무엇: 흐릿한 작은 이미지를 먼저 보여 주고 원본이 도착하면 선명하게 전환하는 이미지 로딩 방식.
- 언제: 큰 사진, 갤러리, 히어로 이미지.
- 피할 때: 아이콘, 작은 썸네일, 텍스트가 든 이미지(흐린 상태를 읽을 수 없다).
- 구현 주의: 수십 바이트~수 KB 크기의 저해상도 미리보기를 CSS `filter: blur(20px)`로 확대해 두고 원본이 로드되면 200~400ms 페이드. 이미지 종횡비를 미리 지정해 레이아웃이 움직이지 않게 한다. 대체 텍스트는 처음부터 제공.
- 비슷한 것: 스켈레톤(단색 자리표시, 이미지 정보 없음).

### 낙관적 UI (Optimistic UI)
- 무엇: 서버 응답을 기다리지 않고 성공한다고 가정해 먼저 화면을 바꾸고, 실패하면 되돌리는 방식.
- 언제: 좋아요, 체크, 순서 변경, 메시지 전송처럼 성공 확률이 높고 가벼운 행동.
- 피할 때: 결제, 삭제 같은 되돌리기 어려운 행동, 서버의 판단이 결과를 바꾸는 행동.
- 구현 주의: 실패하면 원래 상태로 복구하고 이유를 알린다(스낵바나 항목 옆 오류). 전송 중인 항목은 약간 흐리게 하는 등 보류 상태를 구분하면 신뢰도가 높다. 중복 요청, 순서 꼬임을 막는다. 오프라인 대기열이 있으면 재시도 상태를 보여 준다.
- 비슷한 것: 낙관적 반영 뒤의 완료 표시는 [indicators-completion.md](indicators-completion.md).

### 스트리밍 텍스트 (Streaming text)
- 무엇: 전체 결과를 기다리지 않고 생성되는 글을 도착하는 대로 이어서 보여 주는 방식.
- 언제: AI 답변, 긴 요약 생성, 로그 보기.
- 피할 때: 부분적으로 보이면 오해를 부르는 내용(금액, 법적 안내), 끝난 뒤에만 의미가 있는 결과.
- 구현 주의: 자동 스크롤은 사용자가 위로 스크롤하면 멈추고 `맨 아래로` 버튼을 준다. 문장 중간에 레이아웃이 튀지 않게 한다. 스크린 리더는 `aria-live`를 `polite`로 하되 토큰마다 읽지 않도록 완성된 단위로 알린다. 중지 버튼을 제공. 채팅 화면에서의 구성은 [ai-chat.md](ai-chat.md)의 스트리밍 답변.
- 비슷한 것: 타이핑(text 등장 효과, [motion.md](motion.md)는 연출이고 이 항목은 실제 도착 데이터).

### 로딩 버튼 (Loading button)
- 무엇: 누른 버튼 안에서 스피너로 처리 중임을 알리고 다시 못 누르게 하는 버튼 상태.
- 언제: 저장, 제출, 결제, 로그인처럼 한 번의 요청이 걸린 행동.
- 피할 때: 요청 시간이 길고 다른 작업을 계속해야 할 때(백그라운드 진행 표시).
- 구현 주의: 폭과 높이를 유지한다. 스피너 + 라벨(`저장 중…`). 중복 제출 방지. `aria-busy`와 `aria-live`. 실패 시 즉시 복구하고 오류 이유를 안내. 버튼 상태 일람은 [inputs.md](inputs.md)의 로딩.
- 비슷한 것: 스피너(버튼 밖의 영역용).
