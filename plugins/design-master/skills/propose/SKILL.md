# 시안 제안과 선택

디자이너가 아닌 사용자가 화면 UI를 고를 수 있도록, 결정 지점마다 시안을 비교해서 보여 주고 선택을 받는다.

## 지식 위치

- 색인: `${CLAUDE_PLUGIN_ROOT}/references/index.md`
- 결정 순서: `${CLAUDE_PLUGIN_ROOT}/references/decision-order.md`
- 품질 규칙: `${CLAUDE_PLUGIN_ROOT}/references/quality-rules.md`
- 시안 틀: `${CLAUDE_PLUGIN_ROOT}/templates/draft.html`
- 변수가 치환되지 않으면 이 스킬 폴더 기준 `../../`를 앞에 붙인다.

## 절차

### 1. 파악
대상 화면의 다음을 알아낸다. 코드나 문서에서 알 수 있는 것은 직접 읽어서 알아내고, 사용자에게는 모르는 것만 묻는다. 모를 때는 한 번에 한 질문만 한다.
- 화면의 목적과 사용자가 가장 먼저 할 일(주 행동)
- 사용자(누가 쓰나)와 플랫폼(웹, 모바일, 둘 다)
- 대상 레포의 기존 스타일: 색, 폰트, 간격과 토큰, 기존 컴포넌트, 쓰는 UI 라이브러리. 레포의 `CLAUDE.md`나 `AGENTS.md`에 UX 규칙이 있으면 그것이 우선한다.
- 화면에 들어갈 실제 내용(문구, 항목, 데이터 모양)

### 2. 결정 지점 고르기
`decision-order.md`의 8개 지점 중 이 화면에 필요한 것만 골라 번호 목록으로 사용자에게 보여 준다. 각 지점의 "건너뛰어도 되는 조건"에 해당하면 빼고 이유를 한 줄로 쓴다. 지점이 4개를 넘으면 순서를 정해 하나씩 진행한다고 알린다. 지점 1(목적과 주 행동)은 시안 없이 채팅으로 확인만 하고 결정을 `decisions.md`에 적는다. 사용자가 목록을 고치면 반영한다.

### 3. 지점마다 시안 만들기
1. `index.md`로 해당 지점의 레퍼런스 파일을 찾아 읽는다.
2. 이 화면 상황에 맞는 후보 2~4개를 고른다. 각 후보의 "언제"와 "피할 때"를 이 화면에 대조해 근거로 쓴다. 추천 후보를 하나 정하고 이유를 쓴다.
3. `draft.html`을 바탕으로 한 HTML 파일에 후보를 나란히 그린다. 틀의 `FILL` 주석을 채우고 예시 마크업을 지운다. 후보마다 표시할 것: 라벨(A, B, C), 패턴 이름, 이 상황에서의 장점과 단점, 추천 여부와 이유.
4. 저장: `docs/ux-concepts/<slug>/step-NN-<지점>.html` (NN은 01부터, `<slug>`는 화면 이름의 영어 소문자 kebab-case, `<지점>`은 영어 kebab-case 예: `step-02-navigation.html`). 폴더가 없으면 만든다.
5. 브라우저로 연다. PowerShell은 `Start-Process <경로>`, Git Bash는 `start "" <경로>`, macOS는 `open <경로>`, Linux는 `xdg-open <경로>`.

### 4. 선택 받기
- 채팅에서 선택을 받는다. `AskUserQuestion` 도구가 있으면 후보 라벨과 한 줄 요약을 선택지로 쓴다. 없으면 "A, B, C 중 어느 것으로 할까요?"라고 묻는다.
- 사용자가 후보 밖의 것을 원하거나 후보를 섞고 싶어 하면(예: "A의 레이아웃에 B의 색") 그 지점을 다시 그려 새 시안으로 보여 준다. 추측으로 확정하지 않는다.
- 사용자가 추천대로 하라고 하면 추천 후보로 확정한다.

### 5. 기록과 다음 지점
- 선택과 이유를 `docs/ux-concepts/<slug>/decisions.md`에 누적한다. 형식은 아래와 같다.
- 다음 지점의 시안은 앞에서 고른 것을 반영한 화면 위에 그린다. 앞 선택이 뒤 지점의 후보를 바꾸면 그 점을 알린다.
- 이미 기록된 선택을 사용자가 바꾸면 decisions.md를 고치고 영향을 받는 뒤 지점을 다시 확인한다.

### 6. 마무리
- 모든 선택을 합친 최종 시안 `docs/ux-concepts/<slug>/final.html`을 만든다(후보 비교가 아니라 하나의 완성 화면, 필요하면 상태별 화면도 함께). 브라우저로 연다.
- 사용자에게 build로 구현을 넘길지 묻는다. 허락 전에는 운영 코드를 건드리지 않는다.

## decisions.md 형식

```
# <화면 이름> 결정 기록

- 대상 레포: <이름>
- 플랫폼: <웹|모바일|둘 다>
- 주 행동: <한 문장>
- 스타일 기준: <레포의 기존 토큰 요약>

## 결정

### 1. <결정 지점>
- 선택: <후보 라벨과 패턴 이름>
- 이유: <한 문장>
- 시안 파일: step-01-....html
- 고려했으나 고르지 않은 것: <이름과 이유>
```

## 시안 품질 규칙

- 대상 레포의 실제 색, 폰트, 콘텐츠를 쓴다. lorem ipsum과 `Item 1` 같은 자리 글자를 쓰지 않는다.
- 모바일 화면은 약 390px 폭 프레임 안에 그린다. 웹은 데스크톱과 좁은 폭을 모두 확인할 수 있게 한다.
- 후보끼리는 해당 결정 지점만 다르고 나머지는 모두 같게 해서 비교가 되게 한다.
- `quality-rules.md`(Q01~Q16)를 지킨다. 특히 대비, 터치 영역, 포커스 표시, 상태.
- 외부 리소스(CDN, 웹 폰트, 이미지 URL) 없이 파일 하나로 열린다. 이미지가 필요하면 CSS나 인라인 SVG로 대신한다.
- 라이트와 다크에 모두 대응한다(`prefers-color-scheme`과 토글).
- 후보는 실제로 동작하는 수준으로 그린다(눌림, 열림). 모션 후보는 각 후보의 시안 영역에 `재생` 버튼을 두어 누르면 한 번 재생되게 한다(`draft.html`의 `data-play` 버튼과 `.demo-motion`, `.playing` 패턴). 틀은 비교를 위해 시안 영역의 모션을 막지 않고, 모션 감소 설정이 켜진 환경에서는 `.motion-note`가 그 사실을 알린다. 제품 코드의 모션은 `prefers-reduced-motion`을 따른다고 시안에 적는다.

## 규칙

- 아티팩트(claude.ai 게시)는 사용자가 요청할 때만 올린다. 기본은 레포 안 HTML 파일과 브라우저다.
- 운영 코드, 데이터 연동, 설정 파일을 바꾸지 않는다. 쓰는 곳은 `docs/ux-concepts/<slug>/`뿐이다.
- 대상 레포가 시안 위치나 개수를 따로 정해 둔 규칙(예: `concept-01..03` 3종 요구)이 있으면 그 규칙을 먼저 알려 주고 사용자와 맞춘다. 임의로 어기지 않는다.
- 후보가 하나뿐이면(선택지가 없는 지점) 시안을 만들지 않고 결정 사유만 decisions.md에 적고 넘어간다.
