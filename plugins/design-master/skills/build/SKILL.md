# 선택한 디자인 구현

`docs/ux-concepts/<slug>/`의 결정을 대상 레포 코드로 옮긴다. 지식은 스택 중립이고 구현은 대상 레포의 스택을 따른다.

## 지식 위치

- 색인: `${CLAUDE_PLUGIN_ROOT}/references/index.md`
- 결정 순서: `${CLAUDE_PLUGIN_ROOT}/references/decision-order.md`
- 품질 규칙: `${CLAUDE_PLUGIN_ROOT}/references/quality-rules.md`
- 변수가 치환되지 않으면 이 스킬 폴더 기준 `../../`를 앞에 붙인다.

## 절차

### 1. 입력 확인
- 대상 레포와 화면을 확인한다. 레포의 `CLAUDE.md`와 `AGENTS.md`를 먼저 읽는다. 그 규칙이 이 스킬보다 우선한다(브랜치, 커밋, 테스트, UX 절차 등).
- `docs/ux-concepts/<slug>/decisions.md`와 `final.html`을 읽는다. 여러 `<slug>`가 있으면 어느 화면인지 사용자에게 확인한다.
- 기록이 없으면 propose로 먼저 시안을 고르는 것을 권한다. 사용자가 바로 구현을 원하면 다음을 한다.
  1. `decision-order.md`를 따라 이 화면에 필요한 결정 지점의 선택을 스스로 내린다(각 지점의 레퍼런스 파일을 읽고 "언제"와 "피할 때"로 판단).
  2. 선택 내역과 근거를 사용자에게 보고하고 사용자 확인을 받은 뒤에 구현한다. 확인 전에는 코드를 쓰지 않는다.
  3. 같은 내용을 `decisions.md`로 저장해 이후 점검의 기준으로 삼는다.

### 2. 레포 파악
- 스택(프레임워크, 스타일링 방식), 기존 컴포넌트, 디자인 토큰(색, 간격, 반경, 그림자), 아이콘 세트, 반응형 방식을 읽어서 파악한다.
- 기존 디자인 시스템이 있으면 그것을 따른다. 새 토큰이나 새 컴포넌트를 함부로 만들지 않는다. 시안의 값이 레포 토큰에 없으면 가장 가까운 기존 토큰을 쓰고, 다르게 한 것을 보고에 적는다.
- 새로 필요한 의존성은 추가하기 전에 사용자에게 알린다.

### 3. 구현
- 시안의 구조와 선택을 그대로 옮긴다. 시안에 없는 기능이나 장식을 더하지 않는다.
- 결정된 모든 상태(빈 화면, 로딩, 오류, 완료, 버튼과 입력 상태)를 구현한다. 시안에 정상 상태만 있어도 `decision-order.md`의 "상태"와 `quality-rules.md`의 Q08에 따라 필요한 상태를 채운다.
- 해당 요소의 레퍼런스 항목의 "구현 주의"(크기, 지속 시간, 접근성)를 코드에 반영한다. 모션은 `prefers-reduced-motion`을 처리한다.
- 요청 범위 밖의 리팩터링을 하지 않는다. 커밋, push, PR은 레포 규칙과 사용자 지시를 따른다(요청이 없으면 하지 않는다).

### 4. 점검
- `quality-rules.md`의 Q01~Q16으로 자체 점검한다. 위반을 찾으면 고친다.
- 실행 가능하면(개발 서버, 빌드) 실제로 띄운다. 무거운 설치나 빌드는 사용자에게 먼저 알린다. 데스크톱 폭과 모바일 폭(약 390px)에서 화면을 본다. 브라우저 도구가 있으면 스크린샷과 콘솔 오류를 확인하고, 없으면 확인하지 못한 점을 보고에 적는다.
- `decisions.md`의 항목을 하나씩 대조해 구현되었는지 확인한다. 상태별 화면(빈 화면, 로딩, 오류)을 실제로 일으켜 본다.
- 레포의 기존 테스트와 린트가 있으면 돌린다.

### 5. 보고
- 구현한 것(파일과 요약)
- `decisions.md`와 다르게 한 것과 이유
- 확인한 방법(무엇을 어느 폭에서 어떻게 봤는지, 실행한 명령과 결과)
- 남은 것(확인하지 못한 것, 후속 작업)

## 규칙

- 대상 레포의 규칙, 스택, 토큰이 우선이다.
- 선택한 결정과 다르게 구현해야 하면 임의로 바꾸지 않고 이유와 함께 보고한다. 큰 차이면 구현 전에 사용자에게 묻는다.
- 비밀 값(키, 토큰)을 코드나 출력에 넣지 않는다.
