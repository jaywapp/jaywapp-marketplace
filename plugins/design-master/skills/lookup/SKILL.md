# UI 요소 질문 답하기

UI 요소의 이름, 쓸 상황, 구현 주의를 `references/`의 지식으로 답한다. 한국어로 답하고, 설명은 짧게, 판단 기준은 분명하게 쓴다.

## 지식 위치

- 색인: `${CLAUDE_PLUGIN_ROOT}/references/index.md`
- 이 변수가 치환되지 않으면 이 스킬 폴더 기준 `../../references/index.md`를 쓴다.

## 절차

1. 색인(`index.md`)을 읽는다. 질문에 맞는 파일과 항목 이름을 찾는다. 파일 전체를 읽지 말고 필요한 파일만 읽는다.
2. 질문 유형을 정하고 아래 방식으로 답한다.
3. 레퍼런스에 없는 요소면 일반 지식으로 답하되 "레퍼런스에 없는 항목이라 일반적인 설명입니다"라고 밝힌다. 레퍼런스에 있는 것을 일반 지식으로 덮어쓰지 않는다.
4. 사용자가 보여 달라고 하면 아래 "데모 만들기"를 한다.

## 질문 유형

### 이름으로 묻기 ("스낵바가 뭐야")
- 해당 항목의 무엇, 언제, 피할 때, 구현 주의를 요약한다. 비슷한 것이 있으면 차이를 한 줄로 덧붙인다.
- 영어와 한글 이름을 함께 알려 준다(검색이나 개발자 대화에 쓸 수 있도록).

### 상황으로 묻기 ("저장 완료를 뭘로 알려줘")
- 후보 2~3개를 제시하고 고르는 기준을 한 줄씩 쓴다. 마지막에 이 상황에 맞는 하나를 추천하고 이유를 말한다.
- 후보가 헷갈리는 짝이면 `confusable-pairs.md`의 기준을 우선한다. 알림 계열은 `feedback.md`의 "한눈에 고르기" 표를 쓴다.
- 질문에 상황 정보가 부족해 답이 갈리면(되돌릴 수 있는가, 모바일인가) 한 번에 하나만 되묻는다.

### 생김새로 묻기 ("아래에서 올라오는 패널은 뭐야", "점 세 개 메뉴")
- 사용자가 설명한 모습과 맞는 후보 1~3개를 이름과 함께 제시한다. 확신이 낮으면 그렇다고 말하고 구별하는 단서(위치, 동작, 배경이 막히는지)를 묻는다.
- 이름을 찾았으면 이름 질문처럼 쓰임을 간단히 덧붙인다.

### 비교 ("A랑 B 차이")
- `confusable-pairs.md`에 있는 쌍이면 그 표의 기준 한 줄과 각각 맞는 예를 먼저 말한다. 그다음 놓치기 쉬운 점을 한두 개 더한다.
- 표에 없는 쌍이면 두 항목의 "언제"와 "피할 때"를 대조해 말한다.

## 답변 형식

- 결론(이름 또는 추천)을 첫 문장에 둔다.
- 구체 수치는 레퍼런스에 있는 것만 쓴다(크기, 지속 시간 등).
- 답변 끝에 근거 파일을 한 줄로 밝힌다(예: `근거: references/feedback.md`).

## 데모 만들기 (사용자가 "보여 줘", "데모", "직접 눌러 보고 싶어"라고 할 때만)

1. `${CLAUDE_PLUGIN_ROOT}/templates/demo.html`을 읽는다. 이 틀의 `FILL` 주석과 예시 데모(스낵바)를 대상 요소로 바꾼다.
2. 데모는 파일 하나로 열려야 한다(외부 리소스 없음). 실제로 조작되어야 한다(눌림, 열림, 닫힘, 상태 변화). 라이트와 다크 모두 확인한다.
3. "언제 쓰나"와 "피할 때" 카드는 해당 레퍼런스 항목에서 가져온다.
4. 저장 위치:
   - 대상 레포가 분명할 때(사용자가 레포를 지정했거나 대화가 그 레포의 화면에 관한 것일 때)만 그 레포의 `docs/ux-concepts/_demos/<요소-이름>.html`에 저장한다(이름은 영어 소문자 kebab-case).
   - 그렇지 않으면(현재 디렉터리가 우연히 어떤 저장소일 뿐일 때 포함) 임시 폴더(시스템 임시 디렉터리)에 저장한다.
5. 브라우저로 연다. PowerShell은 `Start-Process <경로>`, Git Bash는 `start "" <경로>`, macOS는 `open <경로>`, Linux는 `xdg-open <경로>`.
6. 만든 파일 경로와 보는 법을 알린다.

## 하지 않는 것

- 화면 전체를 설계하거나 코드를 구현하지 않는다(propose, build).
- 기존 화면의 문제를 점검하지 않는다(review).
- 레퍼런스에 없는 내용을 레퍼런스에 있는 것처럼 말하지 않는다.
